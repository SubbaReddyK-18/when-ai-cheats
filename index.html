ABSTRACTWe tested how easily a model can fake a good score, using pure noise, two UCI datasets and 309 years of sunspot data. Picking features before cross-validation gave 81.4% accuracy on random labels; duplicates and a look-ahead feature also flattered results, while scaling before the split hardly mattered. Our tool, LeakageGuard, caught 134 of 200 planted leaks with no false alarms on 200 clean cases.

01The Accuracy Illusion

Our experimentWe started with coin flips. We made random labels, gave a model 10,000 columns of pure noise and tested it with five-fold cross-validation, 30 times over. It should have scored about 50%. It scored 81.4%.

Nothing was wrong with the model. The problem was one line in our own code: we picked the “best” features before splitting the data, so the test rows had already helped choose them. Our title promised 99%, so we kept going; with 50 samples the same mistake reached 99.7%. That is data leakage, and nothing crashes to warn you.

02Why High Accuracy Can Mislead

LiteratureEvaluation estimates how a model will behave on unseen data. If test information shapes training, the score measures apparent performance instead of generalisation performance. The problem is common: a survey of prior reviews found leakage in at least 294 papers across 17 fields, and in one re-examined field complex models lost their advantage over logistic regression once it was fixed [1].

03What Data Leakage Actually Means

LiteratureLeakage is information about the target that should not be legitimately available when learning [2], or information used in training that would not exist at prediction time [3]. Figure 1 shows the failure path and Figure 2 contrasts the incorrect and correct pipelines. Selection bias of this kind was demonstrated on gene-expression data [4], and tuning inside the same cross-validation loop causes a related bias [5].

04Six Major Types of Data Leakage

LiteratureFeature selection leakage chooses features using test labels [4]. Target leakage uses a feature that encodes the outcome [2]. Preprocessing leakage fits scalers or imputers on all rows [3]. Duplicate leakage puts identical or near-identical samples on both sides of a split; 3.3% of CIFAR-10 test images have near-duplicates in training [6]. Temporal leakage trains on the future, so structured data needs blocked or forward splits [7], [8]. Augmentation leakage is the same non-independence, created when augmentation runs before splitting. Language models add benchmark contamination [9].

05Study Design

Our experimentWe ran five experiments in scikit-learn [10] (Table 1). Each one separates synthetic demonstrations, natural dataset properties and leakage we injected deliberately. Datasets: Breast Cancer Wisconsin [11], Optical Digits [12] and yearly sunspots bundled with statsmodels [13]. In E3–E5 every estimate is compared with a reality set never used for estimation.

Our experimentLogistic regression is a linear baseline, random forests ignore feature scale and RBF SVMs are scale-sensitive, so scaling was tested only with the two scale-sensitive models. Variance selection ignores labels, which makes it a control. We used stratified folds for classification, group-aware folds for copied images and forward-chaining splits for time, with t-based 95% confidence intervals over repetitions.

06Python Implementation and Methodology

The decisive difference is one line. Every script fixes its seeds and writes raw results to CSV; the full suite runs in about 40 minutes on one CPU core.

# Leaked: the selector sees every label, then cross-validation runs
X_sel = SelectKBest(f_classif, k=20).fit_transform(X, y)
leaked = cross_val_score(LogisticRegression(max_iter=1000), X_sel, y, cv=cv)

# Correct: the selector is refitted inside every training fold
pipe = Pipeline([("select", SelectKBest(f_classif, k=20)),
                 ("model", LogisticRegression(max_iter=1000))])
correct = cross_val_score(pipe, X, y, cv=cv)

07Results and Analysis

Our experimentLeaked selection averaged 81.4% (SD 3.0) on noise and beat the correct pipeline (50.6%, 95% CI 49.1–52.0) in all 30 runs (Figure 4).

Our experimentThe leak follows the labels (Figure 5). ANOVA-F selection inflated all three classifiers to 74–78%, and mutual information to 52–60%. Label-free variance selection stayed at chance whether done before or inside the folds, so using labels outside the folds, not selection itself, causes the inflation.

Our experimentReal data told a quieter story (Figure 6, Table 2). Scaling before cross-validation moved the breast-cancer estimate by just 0.07 points. Selection with planted noise added 1.3 points for logistic regression and SVM (95% CI 1.0–1.7), small because real features dominate. Exact duplicates inflated naive Digits estimates by 1.5–2.9 points, while group-aware folds matched reality. One-pixel-shifted copies did not leak at all.

Our experimentOn sunspots, shuffled cross-validation estimated a random-forest error of 10.4 and forward-chaining 12.5, yet future years gave 18.2. Later solar cycles were bigger, so both were too hopeful, and shuffling made it worse; with a non-stationary series this fits evidence that K-fold suits only well-behaved autoregressive cases [14]. A look-ahead moving average promised 5.3. Our first version of this test was itself leaky, so we fixed the comparison: the best legitimate model scored 14.6.

FindingLeakage has no fixed size. Here it ranged from 0.07 points for scaling to 31 points for feature selection on noise, depending on the type of leak and how strong the real signal was.

08The LeakageGuard Prototype

ProposedLeakageGuard v2.1 is our Python auditor with five modules (Figure 7): integrity checks, exact and nearest-neighbour duplicate detection, single-feature dependency tests, pipeline checks (a data-level scaling test, a static code scan and a label-permutation canary adapted from established permutation tests [15]) and evaluation checks for shared IDs, groups and time order. Ten unit tests cover positive and negative cases.

Our experimentThen we tried to break it. We planted 200 leaks of 11 kinds and mixed in 200 clean cases (Figure 8). The first run exposed two bugs in our own code: the single-feature tree was too shallow for ten classes, and blank pixel columns confused the scaling test. We fixed both and re-ran everything on new random seeds, so the fix could not simply fit the old cases. Version 2.1 caught 134 of 200 leaks (recall 67%, precision 100%, F1 0.80), gave zero false alarms and took about 0.37 seconds per check.

Our experimentIt is not magic. It missed every shifted image copy, every weak target proxy and every min-max scaling leak, and caught only 85% of jittered duplicates and strong proxies. Those cases need a person who knows the data, or smarter similarity measures [6]. Think of it as a smoke alarm, not a guarantee: a tested prototype, not a production tool.

09How Developers Can Prevent Leakage

LiteratureSplit first, put every fitted step inside a Pipeline [3], use group or forward splits when rows are related [7] and keep a final set untouched. Figure 9 is a printable checklist.

10Limitations and Reproducibility

Our noise is independent and Gaussian, the real datasets are small, and the Digits writers are unknown, a hidden dependency we could not control. Leaks in E3, E4 and the benchmark were planted by us, and we wrote the code corpus ourselves, which favours our tool. All code, seeds, raw results and tests are included (scikit-learn 1.8.0, NumPy 2.4.4, statsmodels 0.15.0).

11Contribution and Conclusion

Our experimentNone of this is new science; researchers have warned about leakage for years [2], [1]. What we add is a side-by-side test of five kinds of leakage against real held-out data, a checking tool that publishes its own misses, and a checklist anyone can use. Our main lesson is simple: when a score looks too good, check what the model was allowed to see.
